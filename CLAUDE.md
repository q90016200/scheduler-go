## Commands

- Run server: `go run main.go` (reads config from `.env` in repo root)
- Run DB migrations: `go run cmd/migrate/migrate.go` (auto-migrates `User`, `Task`, `TaskGroup`, `TaskExecutionLog`)
- Docker image: `docker build -t schedule-go .` (repo-root multi-stage `Dockerfile`: node builds `web/dist` → Go builds `server` + `migrate` → `alpine`, non-root, `HEALTHCHECK` on `/healthz`). Config comes only from env (`--env-file .env`); `.dockerignore` excludes `.env`. Run migrations with `docker run --env-file .env schedule-go ./migrate`.
- Local Postgres: `cd docker && docker compose up -d`. `.env.example` defaults already point at it, so `cp .env.example .env` is enough for local dev.
- Test: `go test ./...`. Single test: `go test -run TestName ./internal/scheduler/`. Race-sensitive scheduler code should be checked with `go test -race ./internal/scheduler/...`.
- Frontend (`/web`, Vue3 + TypeScript + Vite): `cd web && npm install`, `npm run dev` (dev server, proxies `/api` to the Go backend per `web/vite.config.ts`), `npm run build` (outputs `web/dist`, served by the Go binary in production — see `internal/router/router.go`'s `NoRoute` SPA fallback). There is no separate lint script — type-checking happens via `vue-tsc -b` inside `npm run build`.

## Architecture

Gin HTTP API + cron-based task scheduler, backed by PostgreSQL via GORM.

**Layering**: `controllers` (gin handlers, request binding/validation) → `services` (business logic, direct GORM CRUD) → `models` (GORM structs + request DTOs). There is **no repository layer** — `services` hold a `*gorm.DB` directly. This was a deliberate simplification (repositories were a thin pass-through with no independent logic).

**Wiring** (`main.go`): `config.LoadConfig()` (no argument — `.env` path is hardcoded inside) → `logger.Init` → `database.InitializeDB` → `scheduler.NewCronScheduler(db)` → `app.NewAppServices(db, cronScheduler)` → `router.SetupRouter`. `app.AppServices` is the single dependency-injection struct passed to controllers. `LoadConfig` calls `log.Fatalf` (listing every missing key at once, not just the first) if `SERVER_PORT`, `APP_SECRET`, or any `POSTGRES_*` value is empty, so a misconfigured `.env` fails fast at startup rather than binding a random port, running with an empty JWT secret, or failing later at first DB use. Defaults for optional keys (`APP_ENV`, `TOKEN_EXPIRY`, `EXECUTION_LOG_RETENTION_DAYS`, `POSTGRES_SSLMODE`, `POSTGRES_MAX_OPEN_CONNS`/`MAX_IDLE_CONNS`/`CONN_MAX_LIFETIME_MINUTES`) go through `viper.SetDefault`, which only applies when the key is entirely unset — an explicit but invalid value (e.g. `TOKEN_EXPIRY=0`) still needs its own `<= 0` fallback check in code. `TIMEZONE` (default `Asia/Taipei`) is loaded once in `LoadConfig` via `time.LoadLocation` (`log.Fatalf` if invalid; `config.go` blank-imports `time/tzdata` so this works in images without system tzdata) and assigned straight to `time.Local` — there's no separate config field; `time.Local` is the single source for the cron scheduler (robfig/cron defaults to `time.Local`, captured at `cron.New`, so `LoadConfig` must run before `NewCronScheduler`), the Postgres DSN's `TimeZone` (`time.Local.String()`), and log timestamps, so schedules don't silently shift with the host/container's local zone. Per-task override is robfig/cron's built-in `CRON_TZ=Zone ` schedule prefix (accepted by both `cron.ParseStandard` validation and `AddFunc`). `Config.IsDevelopment()` is the one place `AppEnv == "development"` is compared, used by both `main.go` (to skip `gin.SetMode(gin.ReleaseMode)`) and `pkg/logger.resolveLogLevel`. The HTTP server (`http.Server` with explicit `Read`/`Write`/`Idle` timeouts, not bare `r.Run()`) is started in a goroutine; `main` then blocks on `SIGINT`/`SIGTERM` and, on receipt, stops the cron scheduler before calling `srv.Shutdown` with a 10s timeout — so in-flight requests and the scheduler both get a chance to finish instead of being killed mid-request.

**Import-cycle constraint**: `internal/scheduler` is imported by `internal/services` (for `RegisterTaskJob`/`UnregisterTaskJob` when tasks are created/updated/deleted). Because of this, `scheduler` cannot import `services` back — `CronScheduler` therefore keeps its own direct `*gorm.DB` reference and re-implements its own minimal task query in `cron.go` instead of depending on `TaskService.ListTasks`. Keep this direction in mind before adding new cross-package calls between the two.

**Scheduler** (`internal/scheduler/`):
- `cron.go`: `CronScheduler` wraps `robfig/cron/v3` with `cron.Recover(...)` in the chain (a panicking job — e.g. an unhandled HTTP method — is caught and logged instead of crashing the whole process) plus `cron.SkipIfStillRunning(...)`. A fixed every-minute cron job polls `tasks` where `status = enabled`; for each one it calls `registerIfStillEnabled`, which first skips tasks already in `taskCronEntryIDs`, then re-`SELECT`s that one task's current status **while holding `cs.mu`** and registers under the same lock hold (via `registerTaskJobLocked`, the lock-already-held half `RegisterTaskJob` now delegates to) instead of trusting the poller's earlier batch snapshot. This closes a race: every mutating service path commits its DB change *before* calling `UnregisterTaskJob` (which also takes `cs.mu`), so a task disabled/deleted between the poller's batch `SELECT` and this per-task recheck is guaranteed to already be gone from the DB by the time the recheck runs, and can no longer be resurrected into cron. This poller only ever *adds* jobs — it never removes one on its own, so anything that flips a task away from `enabled` (directly, or via the group cascade below) must still explicitly call `scheduler.UnregisterTaskJob`, or the job keeps firing on its old schedule. `registerTaskJobLocked` also removes any cron entry the task's ID already had in `taskCronEntryIDs` before storing the new one, so re-registering an already-registered task (concurrent enable/update, or `CreateTask` racing this same poller) replaces the old entry instead of leaking a second one that fires alongside it. All reads/writes of `taskCronEntryIDs` go through the mutex-guarded `jobCount` helper, `registerIfStillEnabled`, or the existing lock in `RegisterTaskJob`/`UnregisterTaskJob` — the map is touched concurrently from the HTTP handler goroutines and the poller goroutine, so an unguarded read is a data race Go's runtime will `throw` on, not something `recover()` can catch. A second daily cron job (`0 3 * * *`) deletes `TaskExecutionLog` rows older than `config.AppConfig.ExecutionLogRetentionDays` (env `EXECUTION_LOG_RETENTION_DAYS`, default 120).
- `TaskGroup.Status` has no effect on scheduling by itself — the poller above only reads `Task.status`, never `Group.status`. The enforcement lives in `TaskService` (`internal/services/task_service.go`) via the shared `deactivateGroupTasksTx` helper, used by **both** `UpdateTaskGroup` (setting a group to `disabled` bulk-flips its currently-`enabled` tasks to `disabled` and unregisters their cron jobs) **and** `DeleteTaskGroup` (deleting a group does the same cascade before removing the row, then returns the deactivated tasks so the API caller/frontend can surface which tasks were stopped). `deactivateGroupTasksTx` does this as a single `UPDATE ... RETURNING id, name` rather than a `Find` followed by an `Update` — with two separate statements, a task flipped to `enabled` by a concurrent request between them would still get swept up by the blind `UPDATE` but wouldn't appear in the earlier `Find`'s result, so it'd end up disabled in the DB with its cron job never unregistered; `RETURNING` makes "which rows changed" and "what they changed to" atomic in one statement. Setting a group back to `enabled` does **not** cascade — child tasks must be reactivated individually, to avoid a mass-reactivation surprise. Both mutating paths run the DB portion inside `s.db.Transaction(...)`; cron job unregistration (in-memory only) happens after commit. `Task.Group`'s foreign key is `OnDelete:SET NULL`, so deleting a group never deletes its tasks — they just lose their `group_id`; `TaskGroupListView.vue`'s pre-delete confirmation fetches the group's full task count (not just the `enabled` ones) so the user isn't only warned about tasks getting deactivated while the rest silently go orphaned.
- `jobs.go`: per-`Task.Type` execution, each wrapped by `runWithRetry`. `"http"` (`doHTTPAttempt`) uses `resty` for `GET`/`POST`/`PUT`/`DELETE`/`PATCH` against `task.Endpoint` — the method switch has an explicit `default` branch that logs a failed execution instead of leaving `resp`/`err` as `nil` (nothing guarantees the switch stays exhaustive against what validation allows, and a `nil` `resp` would panic). `"rpc"` (`doRPCAttempt`) calls a gRPC service **without precompiled protobuf stubs** — it dials `task.Endpoint`, uses server reflection (`jhump/protoreflect/grpcreflect`) to resolve the service/method described by `task.Method` (format: `"package.Service/MethodName"`), builds the request from `task.Payload` (a JSON string) via `dynamic.NewMessage(...).UnmarshalJSON`, and invokes it with `grpcdynamic.NewStub`. This generic/dynamic design mirrors the schema-less `"http"` job type since job targets are arbitrary and user-configured, not known at compile time. Both attempt functions take a per-call `context.Context` carrying `task.TimeoutSeconds` (default 10 if unset/zero) instead of a hardcoded timeout, and apply `task.Headers` (a free-form JSON `map[string]string`, same schema-less trust model as `Payload`/`Endpoint`) as HTTP request headers or gRPC outgoing metadata respectively — `parseHeaders` silently ignores (logs, doesn't fail the run) a `Headers` value that isn't valid key-value JSON. Every attempt (success or failure) is persisted to `TaskExecutionLog` via `logExecution` — the `Output` column is typed `jsonb` in Postgres (chosen over a plain text column specifically so `output` can later be filtered/aggregated on via Postgres's `jsonb` operators/GIN indexes), so `toJSONColumn` wraps non-JSON output (e.g. plain-text/HTML HTTP bodies) as `{"raw": "..."}` before insert, since Postgres rejects invalid JSON in a `jsonb` column. `TaskExecutionLog.Task`'s foreign key is `OnDelete:CASCADE` (deliberately — the daily retention job above already treats logs as non-permanent), so deleting a task deletes its execution history too.
- **Retry** (`runWithRetry` in `jobs.go`): drives up to `1 + task.RetryCount` attempts (0-5 extra retries), sleeping `task.RetryDelayMs` (0-30000ms, fixed delay, no exponential backoff) between attempts — the inter-attempt sleep is a `select` on the caller's `parentCtx.Done()` vs. the delay timer, so cancelling the batch (see **Run now** below) stops the retry loop from firing again instead of waiting out the full delay first. `doHTTPAttempt`'s success rule is overridable per task via `Task.SuccessStatusCodes` (http only; comma-separated codes or `1xx`-`5xx` classes, e.g. `"200,201,2xx"`, matched by `utils.MatchStatusCode` in `pkg/utils/validator.go` — the same function backs the `status_codes` validator tag by calling it with code `0`, which never matches, so every segment gets parsed). Empty keeps the default (`<400` success). When set, a non-matching code fails, still retryable only if `>=500`; a matching code succeeds even if it's 4xx/5xx (e.g. `404` for an idempotent DELETE). Each attempt function returns a `retryable bool` alongside status/output/errMsg: network errors/timeouts/HTTP 5xx are retryable; HTTP 4xx, unsupported method, bad RPC method format, method-not-found, and payload-unmarshal failures are not (retrying wouldn't change the outcome). Every attempt gets its own `TaskExecutionLog` row (`AttemptNumber` from 1, `IsFinalAttempt` true only on the attempt that ends the loop — either attempts exhausted or a non-retryable result) so the retry history is visible per-run instead of only the final outcome. No system-level cap on total retry wall-clock time exists — `RetryCount`/`RetryDelayMs`/`TimeoutSeconds` are validated independently for range, and it's on the task author to keep a task's worst-case total duration compatible with its own `Schedule` (a long retry chain can make `cron.SkipIfStillRunning` skip the next tick, same tradeoff as any slow job).
- **Failure-streak notifications** (`updateFailureStreakAndNotify` in `jobs.go`, dispatched via `internal/notify`): only runs on the *final* attempt of a *cron*-sourced run (`source == models.SOURCE_CRON`) — manual "Run now" batches never touch `Task.ConsecutiveFailures` or trigger a notification, specifically so testing a task manually can't spuriously fire alerts. A successful final attempt resets `ConsecutiveFailures` to 0 in the DB; a failed one does an atomic `UPDATE ... SET consecutive_failures = consecutive_failures + 1` (avoids a read-modify-write race), then re-reads the row and calls `notify.Dispatch` **only when the new count exactly equals `Task.NotifyFailThreshold`** — this "equals, not >=" check is what makes it fire once and then go silent on subsequent failures (no repeat alerts) until a success resets the counter and the next failure streak can cross the threshold again. `NotifyFailThreshold == 0` means notifications are off for that task regardless of which `Notify*` channel booleans are set.
- `internal/notify`: `Dispatch(task, msg)` fires each enabled channel (`task.NotifyTelegram`/`NotifySlack`) in its own goroutine with a shared 10s `context.Context`, and a channel `Send` failure is only logged (`logger.Log`) — never retried, never surfaced back to the scheduler — mirroring `logExecution`'s "a side-effect failing shouldn't fail the job" stance. Channel credentials/endpoints are global, `.env`-only (`config.AppConfig.NotifyConfig`: `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`, `SLACK_WEBHOOK_URL`) rather than per-task — a task only picks *which* of the two globally-configured channels to use via its two boolean columns, it doesn't supply its own credentials. A channel whose required config is empty just returns `nil` from `Send` without attempting to send (so leaving all three env vars blank is the "notifications entirely off" state, independent of what any task's `Notify*` flags are set to). An email channel existed once and was removed; its `notify_email` column is still in existing databases (GORM `AutoMigrate` never drops columns) and is simply unused — safe to `ALTER TABLE tasks DROP COLUMN notify_email` by hand.
- **Next run time** (`NextRunAt` in `cron.go`): reads `cs.Cron.Entry(entryID).Next` for a task's registered cron entry under the same `cs.mu` lock `jobCount` uses — returns `ok == false` for any task not currently in `taskCronEntryIDs` (disabled, or registration failed), which `TaskService.decorateNextRunAt` (`task_service.go`) turns into a `nil` `Task.NextRunAt` rather than a zero time. Called once per task from `ListTasks`/`GetTask`, not cached — cheap in-memory map lookup, not worth memoizing at current task counts.
- **Execution dashboard** (`TaskExecutionLogService.GetTaskStats` in `task_execution_log_service.go`, `GET /tasks/:id/stats`): three real-time SQL aggregates (30-day success rate, 30-day average duration, fail-count among the last 10 runs), all scoped to `source = 'cron' AND is_final_attempt = true` via the shared `taskStatsQuery` helper — this exclusion is what keeps a task's retry attempts (multiple log rows per logical run) and manual "Run now" testing from skewing the numbers. No caching/materialized table; re-queried on every `TaskDetailView.vue` load. `GetDashboardStats` (same file, `GET /api/dashboard/stats`, its own route group in `router.go` since it needs a path outside `/api/tasks/:id` wildcard) is the site-wide counterpart backing `DashboardView.vue`: enabled/disabled task counts (one `GROUP BY status` query, not two separate `Count`s), 24h execution count/success rate, a top-5 failing-tasks list (`GROUP BY task_id` joined to `tasks`, `models.DashboardFailingTask`), and the list of tasks currently mid failure-streak (`consecutive_failures > 0`, `models.DashboardTaskRef` — no `fail_count` field, since that number isn't meaningful for an in-progress streak). Same `source='cron' AND is_final_attempt=true` scoping as the per-task version, same no-cache philosophy.
- **SSRF guard**: both the `resty` client (`newSSRFGuardedRestyClient` in `cron.go`) and the gRPC dialer (`grpc.WithContextDialer` in `jobs.go`) route through `internal/ssrf.SafeDialContext`, which uses a `net.Dialer.Control` hook to reject connections to loopback, link-local (incl. cloud metadata `169.254.169.254`), and unspecified addresses **at actual-connect time** — checking the resolved IP rather than the pre-resolution hostname, so it isn't bypassable via DNS rebinding. RFC1918 private ranges are deliberately **not** blocked (this is an internal scheduling tool; reaching internal services is its job) — the escape hatch `SSRF_ALLOW_PRIVATE_TARGETS=true` (env, default false) disables the whole guard for cases that genuinely need to hit loopback. `SafeDialContext` lives in `internal/ssrf` rather than `pkg/utils` specifically because its policy — reading `config.AppConfig` — is app-specific; `pkg/` is meant to stay free of reverse dependencies on `internal/`.
- **Run now (`RunTaskNow`/`CancelTaskRun` in `jobs.go`)**: triggered by `POST /tasks/:id/run` (optionally with `{"repeat", "interval_ms"}`, defaulted/validated by the controller to 1–50 times / 100–60000ms). `jobFor` resolves the per-type closure (same `RunRequestHttp`/`RunRequestRpc` the cron path uses) up front, so an unknown `task.Type` is returned as an error synchronously before anything is scheduled, instead of failing inside a goroutine the caller can't observe. Execution itself is async: a goroutine loops `repeat` times with a `time.Sleep`-equivalent `time.After` between calls, writing one `TaskExecutionLog` per call via the same `logExecution` and continuing past a failed call rather than aborting the batch. `CronScheduler.runBatches` (keyed by `task.ID`, guarded by its own `runBatchesMu` — deliberately separate from `taskCronEntryIDs`'s `mu` since the two are unrelated) tracks one `context.CancelFunc` per in-flight batch; a second `RunTaskNow` for the same task while one is running returns `ErrBatchAlreadyRunning` (surfaced as HTTP 409) instead of interleaving two batches against the same task. `DELETE /tasks/:id/run` (`CancelTaskRun`) cancels that context, which aborts the in-flight call as well as any remaining iterations: `RunRequestHttp`/`RunRequestRpc` return `func(ctx context.Context)` instead of a bare `func()`, and `runWithRetry` derives its per-attempt `context.WithTimeout` from that passed-in `parentCtx` (instead of `context.Background()`) and also selects on `parentCtx.Done()` during the inter-retry `RetryDelayMs` sleep — so cancelling the batch context propagates all the way into the in-flight `resty` request (`req.SetContext`) or gRPC call (`stub.InvokeRpc`) and aborts it immediately, and stops any remaining retries from firing instead of burning through the rest of `RetryCount` first. The cancelled attempt is still logged normally via `logExecution` (`status=failed`, `error_message` containing `context canceled`) — no new status value was introduced for this. Every batch's context derives from `CronScheduler.baseCtx`, which `StopCronScheduler` cancels on shutdown; `RegisterTaskJob` (the cron path) also passes `cs.baseCtx` into its `runOnce(ctx)` call for the same reason, so a scheduled run in flight is aborted on shutdown too, not just left to finish. This path still bypasses `cron.SkipIfStillRunning` and can overlap a scheduled run of the same task, same as before. `logExecution` treats a `nil` `*gorm.DB` as a no-op write (rather than panicking) specifically so `jobs_test.go` can exercise real `RunRequestHttp` calls against an `httptest.Server` without a Postgres instance.

**Validation**: `Task.Method`'s required format depends on `Task.Type` (e.g. `GET/POST/PUT/DELETE/PATCH` for `http`, `"pkg.Service/Method"` for `rpc`). This is enforced via a struct-level validator, `utils.ValidateTaskMethod` (`pkg/utils/validator.go`) rather than per-field tags, since the constraint spans two fields. The function body stays in `pkg/utils` (it only uses reflection, no `models` types), but its `RegisterStructValidation(utils.ValidateTaskMethod, models.CreateTaskReq{}, models.UpdateTaskReq{})` call lives in `internal/models/validation.go`'s `init()` instead — registering it directly in `pkg/utils` would have required importing `internal/models` there, a reverse dependency. This split relies on `models` always importing `utils` (true today, since controllers use both) so the `init()` is guaranteed to run before anything validates a task. `Task.Type` is additionally constrained to `oneof=http rpc` and `Task.Schedule` must pass the custom `cron` tag (`checkCronExpr`, backed by the same `cron.ParseStandard` the scheduler itself uses) — both were added so `CreateTask`/`UpdateTask` reject bad input before `RegisterTaskJob` ever runs; `CreateTask` additionally deletes the just-inserted row if registration still fails for some other reason, to avoid orphaned rows. `Task.Headers` uses go-playground/validator's built-in `json` tag (`omitempty,json`) to reject a non-JSON string before it ever reaches `parseHeaders`; `RetryCount`/`RetryDelayMs`/`TimeoutSeconds`/`NotifyFailThreshold` are plain `min`/`max` range tags (0-5 / 0-30000 / 1-120 / 1-20 respectively) — `TaskService.CreateTask`/`UpdateTask` additionally fall back `TimeoutSeconds` to 10 and `Headers` to `"{}"` when the request omits them (a zero-value int/empty string would otherwise be written to the DB as-is, since GORM doesn't apply column `default:` tags when the Go value is explicitly present in an `INSERT`/`UPDATE`).

**Auth**: JWT stored in an `auth_token` cookie (not an `Authorization` header). `internal/auth/jwt.go` issues/parses tokens using `config.AppConfig.AppSecret` (loaded from `.env`'s `APP_SECRET`) and pins `jwt.WithValidMethods([]string{"HS256"})` on parse. **Currently disabled**: `JWTAuthMiddleware()` is not mounted anywhere in `internal/router/router.go`, and the frontend's login-redirect guard (`web/src/router/index.ts`) and `App.vue`'s logged-in-only shell were removed — all API routes and pages are open, temporarily, until login is re-enabled. The auth controller/service/store/views are untouched, so re-enabling is just re-adding the middleware calls and the router guard.

**User management** (`internal/controllers/user_controller.go`, `internal/services/user_service.go`): plain CRUD over `models.User` behind `/api/users`, mirroring the Task/TaskGroup controller→service shape. `User.Status` uses the same `enabled`/`disabled` string convention as `Task.Status`/`TaskGroup.Status` (`models.STATUS_ENABLED`/`STATUS_DISABLED`), so all three share one vocabulary. `AuthService.Authenticate` checks `Status` after the bcrypt password compare and returns `services.ErrUserDisabled` for a `disabled` account, which `AuthController.LoginHandler` maps to a 401 with a distinct message — this check runs on every login attempt regardless of whether `JWTAuthMiddleware` is mounted, since it's inside `Authenticate` itself, not the middleware.

**Response envelope**: all API responses go through `pkg/response.Success`/`Fail`, which wrap payloads in a `{code, message, data, error, trace}` shape and pull `trace_id` from gin context (set by `OpenTracingMiddleware`). Controller error paths intentionally do **not** put the raw Go `error` into the `error` field for unexpected (500-class) failures — it's logged server-side (via `logger.WithTrace(c)`, so it's tied to the same `trace_id` returned to the client) instead, so a bug report can reference the trace without leaking internal error strings to callers. Structured validation errors (`utils.FormatValidationErrors`, per-field `{field, tag, param}`, where `field` is the **json** name — `utils.MyValidator` has a `RegisterTagNameFunc` reading the `json` tag, so it's `endpoint` not `EndPoint`; struct-level `ReportError` calls in `ValidateTaskMethod` pass `"method"` explicitly to match — or a bare `{error}` entry when `ShouldBindJSON` itself fails on malformed/mistyped JSON) are the exception and are still returned to the client, since the frontend parses that array shape into a readable message (see **Frontend API client**'s `formatEnvelopeError` below) rather than just stringifying it.

**Logging** (`pkg/logger/logger.go`): `logger.Log` writes to two sinks with different formats — stdout gets the colored, human-readable `LogFormatter` (includes `entry.Data`, so `trace_id` and `WithError(err)` fields show up); the log file (`logs/app.log`, rotated via `lumberjack`) gets JSON through a `logrus.Hook` (`fileHook`), so `jq 'select(.trace_id=="...")' logs/app.log` works. Level is controlled by `config.AppConfig.LogLevel` (populated from the `.env`/env `LOG_LEVEL` key — not read directly via `os.Getenv`, so it goes through the same `SetDefault`/required-key handling as everything else in `config.LoadConfig`), falling back to `debug` in development (`Config.IsDevelopment()`), `info` otherwise. `OpenTracingMiddleware` (`internal/middleware/tracing_middleware.go`) reuses an incoming `X-Request-ID` header as `trace_id` when present (otherwise generates one) and echoes it back as a response header, so it round-trips through callers that set it. `logger.SetReportCaller(true)` (`logger.go`, `Init`) means every log line's `funcVal` reflects the actual Go runtime symbol of whatever closure called into logrus — for a factory function like `OpenTracingMiddleware()` that returns a `gin.HandlerFunc`, each call site gets its own compiled closure instance and its own `.funcN` suffix (`func1`, `func2`, ...), and the N-to-call-site mapping is decided by the compiler, not by the order the call sites appear in the source. `router.go` therefore calls `middleware.OpenTracingMiddleware()` exactly **once** and reuses that single returned handler across all five `.Group(...).Use(...)` route groups, so every request logs the same, single funcN instead of a different (and unpredictable) one per route group. `OpenTracingMiddleware` itself logs a single "請求完成" line per request (method/path/status/duration_ms) after `c.Next()` returns, rather than separate "start" and "end" lines — halves the log volume, which matters now that several frontend pages poll their APIs automatically every 30–120s (see **Frontend auto-refresh** below).

**Health check**: `GET /healthz` (registered in `router.go` outside `/api`, so it bypasses both the SPA `NoRoute` fallback and `OpenTracingMiddleware`) pings the DB with a 2s timeout — 200 `{"status":"ok"}` or 503. `main.go` builds the engine with `gin.New()` + `gin.LoggerWithConfig{SkipPaths: ["/healthz"]}` + `gin.Recovery()` instead of `gin.Default()` so probe traffic doesn't flood the access log. `SetupRouter` takes `*gorm.DB` as a third argument for this handler only.

**Frontend serving (no CORS)**: the Vue frontend (`/web`) is served same-origin in production via `r.Static`/`r.NoRoute` in `router.go` (serving `web/dist`, with an SPA fallback to `web/dist/index.html` for non-`/api` paths). There is no CORS middleware because it isn't needed: in development, `web/vite.config.ts` already proxies `/api` to the Go backend with `changeOrigin: true`, so the browser's requests stay same-origin against the Vite dev server itself, and production is same-origin by construction. If a future consumer needs true cross-origin browser access (a separate frontend, an embedded widget), CORS middleware would need to be reintroduced deliberately for that case.

**Frontend run-now polling** (`web/src/components/RunTaskDialog.vue`): shared by `TaskListView.vue` and `TaskDetailView.vue`. Before calling `POST /tasks/:id/run` it fetches the task's most recent `TaskExecutionLog` id as a baseline, then polls `GET /tasks/logs/` every second and treats any log whose `id` sorts lexically greater than the baseline **and** whose `source` is `manual` as belonging to this batch — the `source` filter keeps a cron run that happens to land in the same window from being counted, and the lexical-id comparison still relies on `xid` ids being chronologically sortable as plain strings (timestamp-prefixed), rather than on `started_at` (only second-precision, and receiving no batch/run identifier from the backend to filter on directly). Progress and completion are counted off `is_final_attempt` rows only (`completedCount`), not raw row count, since a call that retries writes multiple `TaskExecutionLog` rows per logical call; the poll query's `limit` scales with `form.repeat * (1 + task.retry_count)` accordingly. The client-side wait `deadline` is computed from the task's own `timeout_seconds`/`retry_count`/`retry_delay_ms` (worst-case per call: `timeout_seconds * (1 + retry_count) + retry_delay_ms * retry_count`) instead of a hardcoded per-call allowance, so a task with a long timeout or many retries doesn't get marked "timed out" client-side while it's still legitimately running. An `unmounted` flag is checked after each `await` in `handleSubmit`/`poll` so closing the dialog mid-request can't still spin up the `setInterval` poll timer afterward. Closing the dialog only stops the client-side polling; it does **not** call `DELETE /tasks/:id/run`, so an in-progress batch keeps running server-side unless the user explicitly clicks cancel (which aborts the in-flight call — see **Run now** above). `ExecutionLogTable.vue` (shared by this dialog and every other execution-log listing) has an `el-table-column type="expand"` as its first column showing the full `output`/`error_message` for that row — the existing `output`/`error_message` columns stay truncated (`show-overflow-tooltip`) since they're still useful for at-a-glance scanning; the expand row is for reading a specific run's full output without navigating to `/executions/:id`.

**Frontend auto-refresh** (`web/src/composables/useAutoRefresh.ts`): a small shared composable, `useAutoRefresh(loadFn, intervalMs)`, called from `TaskListView.vue` (120000ms), `AllExecutionsView.vue`/`TaskDetailView.vue`/`DashboardView.vue` (30000ms). It `setInterval`s `loadFn` and tears the timer down `onBeforeUnmount`; it deliberately does **not** touch the calling view's own `loading` ref, so periodic background refreshes swap data in silently instead of flashing the same spinner/skeleton a manual "重新整理" click shows (`load(silent = false)` in each of those views takes a `silent` flag for exactly this — `useAutoRefresh` always calls `load(true)`). A single module-level `autoRefreshEnabled` ref (exported from the same file) gates whether the interval is actually armed, persisted to `localStorage` under `auto-refresh-enabled` (default on) — `App.vue`'s sidebar has one `el-switch` bound to it, so toggling auto-refresh anywhere in the app affects every page's polling, not per-page state.

**Frontend dashboard** (`web/src/views/DashboardView.vue`, route `/dashboard`, the redirect target of `/` in `web/src/router/index.ts`): renders `GET /api/dashboard/stats` (see `GetDashboardStats` above) as four `.kpi` tiles (the "連續失敗中" tile turns red when non-zero) plus two list panels: top-5 failing tasks (with a bar scaled to the top entry's `fail_count`) and currently-failing tasks. There's no hourly breakdown — the stats API doesn't return one. `App.vue`'s sidebar has a "儀表板" entry first in the list.

**Frontend notify-config warning** (`GET /api/notify/config`, `internal/controllers/notify_controller.go`): a tiny stateless controller (no service/DB dependency, constructed with no args) that reflects `config.AppConfig.NotifyConfig`'s two channels back as booleans (`telegram_configured` requires both `TelegramBotToken` and `TelegramChatID` non-empty; `slack_configured` checks `SlackWebhookURL`) — never returns the actual token/webhook. `TaskForm.vue` fetches this once on mount and shows an inline red warning next to a `Notify*` checkbox when it's checked but that channel's `.env` config is missing, so a user isn't left assuming a notification will actually fire just because they ticked the box.

**Frontend shell & visual style** (`web/src/App.vue`, `web/src/style.css`): left sticky sidebar (collapses to a top bar under 860px; hidden on `/login`), active item matched on the route's first path segment so detail pages light up their section. `/users` is intentionally **not** in the sidebar (route kept) until user management is exposed again. Each view is `.page` > `.page-head` (h1 + actions) + `el-card` panels; `.kpis`/`.kpi` are the shared stat tiles. `v-liquid-glass` (`web/src/directives/liquidGlass.ts`, registered globally in `main.ts`) implements kube.io-style liquid glass: it generates a per-element displacement map + rim-highlight image on a canvas (regenerated on resize via `ResizeObserver`, debounced) and sets `backdrop-filter: url(#filter)` — **Chromium only** (gated on `navigator.userAgentData`); other browsers keep the plain CSS `blur` glass from `style.css`. The body's dot grid exists so the edge refraction is actually visible.

**Frontend task identity & kind** : `TaskName.vue` renders every task name with a `#` + last-6-chars short id (full id in `title`) and links to the detail page, so same-named tasks can be told apart anywhere a name shows (task list, dashboard, execution logs, run/edit dialog titles). Task names are **not** unique in the DB; `TaskListView` additionally tags names duplicated within the current page as 「同名」. `TaskKind.vue` color-codes `type` (http/rpc) and HTTP method via the `--kind-*`/`--m-*` tokens in `style.css`. `utils/cron.ts`'s `describeCron` (cronstrue, zh_TW, understands the `CRON_TZ=` prefix) is shared by `CronInput` and the list/detail views.

**Frontend list views**: `composables/usePagedList.ts` owns page/total/loading, `load(silent)`, `reloadFromFirstPage`, and `handleSortChange` for every paged list (`TaskListView`, `TaskGroupListView`, `AllExecutionsView`, `UserListView`). `AllExecutionsView.vue` serves both `/executions` and `/tasks/:id/executions` (optional `id` prop; it `watch`es `id` because Vue Router reuses the instance across the two routes). `StatusSwitch.vue` is the one enabled/disabled `el-switch`; `utils/time.ts`'s `formatTime` is the one timestamp formatter.

**Controller helpers** (`internal/controllers/helpers.go`): `failErr` (404 on `gorm.ErrRecordNotFound`, otherwise log + 500), `bindJSON` (bind + `MyValidator.Struct`, Info log + 400 with `FormatValidationErrors`), `pageParams` (limit 1–100 default 20, offset ≥ 0). `RunTaskHandler` binds by hand because an empty body (`io.EOF`) is allowed there. `UpdateTaskReq`/`UpdateTaskGroupReq` are type aliases of the Create DTOs.

**Frontend back-navigation convention**: detail views use `router.back()` (not a hardcoded `router.push('/some-list')`) for their "返回" action, so the button returns to wherever the user actually came from (task list, dashboard, elsewhere) rather than a fixed page — see `ExecutionLogDetailView.vue` and `TaskDetailView.vue`. No fallback for "no previous history" is implemented; this mirrors the existing `ExecutionLogDetailView.vue` behavior rather than adding new complexity for a rare direct-URL-entry case.

**Frontend API client** (`web/src/api/client.ts`): the single axios instance's response interceptor unwraps the response envelope by returning `res.data.data`, so every function in `web/src/api/*.ts` resolves to the payload itself, not an `AxiosResponse` — cross-reference `pkg/response`'s `{code, message, data, error, trace}` shape above if this isn't obvious from either side alone. Errors are re-thrown as a plain `Error`, built by `formatEnvelopeError`: the envelope's `error` field is either a plain string (used as-is) or the `[{field, tag, param}]` array `utils.FormatValidationErrors` produces for a validation failure, which is joined with `；` between entries — each `field` translated through `FIELD_LABELS` (json name → the form's Chinese label) and each `tag` through `TAG_MESSAGES` (unknown ones fall back to raw `tag param`), and a bare `{error}` entry rendered as `請求格式錯誤：…`; falls back to `env.message` when `error` is empty, and for HTTP ≥500 appends `（trace: …）` from the envelope so a user's bug report carries the id to grep `logs/app.log` with. The same interceptor also does `router.push('/login')` on a 401 — since the frontend's login-redirect route guard was removed along with auth (see **Auth** above), this is currently the *only* remaining path that ever sends a user to `/login`.

**Frontend headers editor** (`web/src/components/TaskForm.vue`): `Task.Headers` is a JSON string on the wire, but the form edits it as a `{key, value}[]` array (`headerRows`) for a normal key-value UI — `parseHeaderRows` deserializes on load, and `handleSubmit` re-serializes (dropping rows with an empty key) into `form.headers` right before emitting, so the JSON round-trip only happens at the two edges of the component.

**Go version**: `go.mod` pins `go 1.27.1` (the Dockerfile's `golang:` builder tag must match). Since 1.27, stdlib `encoding/json` runs on the v2 implementation with v1 semantics preserved; `GOEXPERIMENT=nojsonv2` restores the old implementation if a regression shows up. Nothing here imports `encoding/json/v2` directly. When bumping `google.golang.org/grpc` or `github.com/jhump/protoreflect`, check each candidate version's own `go.mod` `go` directive first — `go get`/`go mod tidy` will otherwise silently bump this project's `go` directive to satisfy a newer dependency.
