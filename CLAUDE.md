## Commands

- Run server: `go run main.go` (reads config from `.env` in repo root)
- Run DB migrations: `go run cmd/migrate/migrate.go` (auto-migrates `User`, `Task`, `TaskGroup`, `TaskExecutionLog`)
- Test: `go test ./...` (covers `internal/scheduler/jobs_test.go` — cron registration/error paths, plus `RunTaskNow`'s repeat count, concurrent-batch rejection, and cancellation — and `internal/ssrf/ssrf_test.go` — the SSRF dial guard). Race-sensitive scheduler code should be checked with `go test -race ./internal/scheduler/...`.
- Frontend (`/web`, Vue3 + TypeScript + Vite): `cd web && npm install`, `npm run dev` (dev server, proxies `/api` to the Go backend per `web/vite.config.ts`), `npm run build` (outputs `web/dist`, served by the Go binary in production — see `internal/router/router.go`'s `NoRoute` SPA fallback).

## Architecture

Gin HTTP API + cron-based task scheduler, backed by PostgreSQL via GORM.

**Layering**: `controllers` (gin handlers, request binding/validation) → `services` (business logic, direct GORM CRUD) → `models` (GORM structs + request DTOs). There is **no repository layer** — `services` hold a `*gorm.DB` directly. This was a deliberate simplification (repositories were a thin pass-through with no independent logic).

**Wiring** (`main.go`): `config.LoadConfig()` (no argument — `.env` path is hardcoded inside) → `logger.Init` → `database.InitializeDB` → `scheduler.NewCronScheduler(db)` → `app.NewAppServices(db, cronScheduler)` → `router.SetupRouter`. `app.AppServices` is the single dependency-injection struct passed to controllers. `LoadConfig` calls `log.Fatalf` (listing every missing key at once, not just the first) if `SERVER_PORT`, `APP_SECRET`, or any `POSTGRES_*` value is empty, so a misconfigured `.env` fails fast at startup rather than binding a random port, running with an empty JWT secret, or failing later at first DB use. Defaults for optional keys (`APP_ENV`, `TOKEN_EXPIRY`, `EXECUTION_LOG_RETENTION_DAYS`, `POSTGRES_SSLMODE`, `POSTGRES_MAX_OPEN_CONNS`/`MAX_IDLE_CONNS`/`CONN_MAX_LIFETIME_MINUTES`) go through `viper.SetDefault`, which only applies when the key is entirely unset — an explicit but invalid value (e.g. `TOKEN_EXPIRY=0`) still needs its own `<= 0` fallback check in code. `Config.IsDevelopment()` is the one place `AppEnv == "development"` is compared, used by both `main.go` (to skip `gin.SetMode(gin.ReleaseMode)`) and `pkg/logger.resolveLogLevel`. The HTTP server (`http.Server` with explicit `Read`/`Write`/`Idle` timeouts, not bare `r.Run()`) is started in a goroutine; `main` then blocks on `SIGINT`/`SIGTERM` and, on receipt, stops the cron scheduler before calling `srv.Shutdown` with a 10s timeout — so in-flight requests and the scheduler both get a chance to finish instead of being killed mid-request.

**Import-cycle constraint**: `internal/scheduler` is imported by `internal/services` (for `AddJob`/`RemoveJob` when tasks are created/updated/deleted). Because of this, `scheduler` cannot import `services` back — `CronScheduler` therefore keeps its own direct `*gorm.DB` reference and re-implements its own minimal task query in `cron.go` instead of depending on `TaskService.ListTasks`. Keep this direction in mind before adding new cross-package calls between the two.

**Scheduler** (`internal/scheduler/`):
- `cron.go`: `CronScheduler` wraps `robfig/cron/v3` with `cron.Recover(...)` in the chain (a panicking job — e.g. an unhandled HTTP method — is caught and logged instead of crashing the whole process) plus `cron.SkipIfStillRunning(...)`. A fixed every-minute cron job polls `tasks` where `status = active`, and diffs against the in-memory `taskCronEntryIDs` map to `AddJob`/`RemoveJob` as tasks are created/updated/deleted or flip status. This poller only ever *adds* jobs for active tasks not yet in the map — it never removes a job on its own, so anything that flips a task away from `active` (directly, or via the group cascade below) must explicitly call `scheduler.UnregisterTaskJob`, or the job keeps firing on its old schedule. All reads/writes of `taskCronEntryIDs` go through the mutex-guarded `hasJob`/`jobCount` helpers or the existing lock in `RegisterTaskJob`/`UnregisterTaskJob` — the map is touched concurrently from the HTTP handler goroutines and the poller goroutine, so an unguarded read is a data race Go's runtime will `throw` on, not something `recover()` can catch. A second daily cron job (`0 3 * * *`) deletes `TaskExecutionLog` rows older than `config.AppConfig.ExecutionLogRetentionDays` (env `EXECUTION_LOG_RETENTION_DAYS`, default 120).
- `TaskGroup.Status` has no effect on scheduling by itself — the poller above only reads `Task.status`, never `Group.status`. The enforcement lives in `TaskService` (`internal/services/task_service.go`) via the shared `deactivateGroupTasksTx` helper, used by **both** `UpdateTaskGroup` (setting a group to `inactive` bulk-flips its currently-`active` tasks to `inactive` and unregisters their cron jobs) **and** `DeleteTaskGroup` (deleting a group does the same cascade before removing the row, then returns the deactivated tasks so the API caller/frontend can surface which tasks were stopped). Setting a group back to `active` does **not** cascade — child tasks must be reactivated individually, to avoid a mass-reactivation surprise. Both mutating paths run the DB portion inside `s.db.Transaction(...)`; cron job unregistration (in-memory only) happens after commit. `Task.Group`'s foreign key is `OnDelete:SET NULL`, so deleting a group never deletes its tasks — they just lose their `group_id`; `TaskGroupListView.vue`'s pre-delete confirmation fetches the group's full task count (not just the `enabled` ones) so the user isn't only warned about tasks getting deactivated while the rest silently go orphaned.
- `jobs.go`: per-`Task.Type` execution. `"http"` uses `resty` for `GET`/`POST`/`PUT`/`DELETE`/`PATCH` against `task.Endpoint` — the method switch has an explicit `default` branch that logs a failed execution instead of leaving `resp`/`err` as `nil` (an earlier version panicked here for any method outside the handled set, since nothing guaranteed the switch was exhaustive against what validation allowed). `"rpc"` calls a gRPC service **without precompiled protobuf stubs** — it dials `task.Endpoint`, uses server reflection (`jhump/protoreflect/grpcreflect`) to resolve the service/method described by `task.Method` (format: `"package.Service/MethodName"`), builds the request from `task.Payload` (a JSON string) via `dynamic.NewMessage(...).UnmarshalJSON`, and invokes it with `grpcdynamic.NewStub`. This generic/dynamic design mirrors the schema-less `"http"` job type since job targets are arbitrary and user-configured, not known at compile time. Every run (success or failure) is persisted to `TaskExecutionLog` via `logExecution` — the `Output` column is typed `jsonb` in Postgres (chosen over a plain text column specifically so `output` can later be filtered/aggregated on via Postgres's `jsonb` operators/GIN indexes), so `toJSONColumn` wraps non-JSON output (e.g. plain-text/HTML HTTP bodies) as `{"raw": "..."}` before insert, since Postgres rejects invalid JSON in a `jsonb` column. `TaskExecutionLog.Task`'s foreign key is `OnDelete:CASCADE` (deliberately — the daily retention job above already treats logs as non-permanent), so deleting a task deletes its execution history too.
- **SSRF guard**: both the `resty` client (`newSSRFGuardedRestyClient` in `cron.go`) and the gRPC dialer (`grpc.WithContextDialer` in `jobs.go`) route through `internal/ssrf.SafeDialContext`, which uses a `net.Dialer.Control` hook to reject connections to loopback, link-local (incl. cloud metadata `169.254.169.254`), and unspecified addresses **at actual-connect time** — checking the resolved IP rather than the pre-resolution hostname, so it isn't bypassable via DNS rebinding. RFC1918 private ranges are deliberately **not** blocked (this is an internal scheduling tool; reaching internal services is its job) — the escape hatch `SSRF_ALLOW_PRIVATE_TARGETS=true` (env, default false) disables the whole guard for cases that genuinely need to hit loopback. `SafeDialContext` lives in `internal/ssrf` rather than `pkg/utils` (where it originated) specifically because its policy — reading `config.AppConfig` — is app-specific; `pkg/` is meant to stay free of reverse dependencies on `internal/`.
- **Run now (`RunTaskNow`/`CancelTaskRun` in `jobs.go`)**: triggered by `POST /tasks/:id/run` (optionally with `{"repeat", "interval_ms"}`, defaulted/validated by the controller to 1–50 times / 100–60000ms). `jobFor` resolves the per-type closure (same `RunRequestHttp`/`RunRequestRpc` the cron path uses) up front, so an unknown `task.Type` is returned as an error synchronously before anything is scheduled, instead of failing inside a goroutine the caller can't observe. Execution itself is async: a goroutine loops `repeat` times with a `time.Sleep`-equivalent `time.After` between calls, writing one `TaskExecutionLog` per call via the same `logExecution` and continuing past a failed call rather than aborting the batch. `CronScheduler.runBatches` (keyed by `task.ID`, guarded by its own `runBatchesMu` — deliberately separate from `taskCronEntryIDs`'s `mu` since the two are unrelated) tracks one `context.CancelFunc` per in-flight batch; a second `RunTaskNow` for the same task while one is running returns `ErrBatchAlreadyRunning` (surfaced as HTTP 409) instead of interleaving two batches against the same task. `DELETE /tasks/:id/run` (`CancelTaskRun`) cancels that context — this only stops the *next* iteration from firing; a call already in flight keeps running to its own 10s timeout, since `RunRequestHttp`/`RunRequestRpc` don't currently accept a context to abort mid-request. Every batch's context derives from `CronScheduler.baseCtx`, which `StopCronScheduler` cancels on shutdown so a run-now batch doesn't keep firing after the process is told to stop. This path still bypasses `cron.SkipIfStillRunning` and can overlap a scheduled run of the same task, same as before. `logExecution` treats a `nil` `*gorm.DB` as a no-op write (rather than panicking) specifically so `jobs_test.go` can exercise real `RunRequestHttp` calls against an `httptest.Server` without a Postgres instance.

**Validation**: `Task.Method`'s required format depends on `Task.Type` (e.g. `GET/POST/PUT/DELETE/PATCH` for `http`, `"pkg.Service/Method"` for `rpc`). This is enforced via a struct-level validator, `utils.ValidateTaskMethod` (`pkg/utils/validator.go`) rather than per-field tags, since the constraint spans two fields. The function body stays in `pkg/utils` (it only uses reflection, no `models` types), but its `RegisterStructValidation(utils.ValidateTaskMethod, models.CreateTaskReq{}, models.UpdateTaskReq{})` call lives in `internal/models/validation.go`'s `init()` instead — registering it directly in `pkg/utils` would have required importing `internal/models` there, a reverse dependency. This split relies on `models` always importing `utils` (true today, since controllers use both) so the `init()` is guaranteed to run before anything validates a task. `Task.Type` is additionally constrained to `oneof=http rpc` and `Task.Schedule` must pass the custom `cron` tag (`checkCronExpr`, backed by the same `cron.ParseStandard` the scheduler itself uses) — both were added so `CreateTask`/`UpdateTask` reject bad input before `RegisterTaskJob` ever runs; `CreateTask` additionally deletes the just-inserted row if registration still fails for some other reason, to avoid orphaned rows.

**Auth**: JWT stored in an `auth_token` cookie (not an `Authorization` header). `internal/auth/jwt.go` issues/parses tokens using `config.AppConfig.AppSecret` (loaded from `.env`'s `APP_SECRET`) and pins `jwt.WithValidMethods([]string{"HS256"})` on parse. **Currently disabled**: `JWTAuthMiddleware()` is not mounted anywhere in `internal/router/router.go`, and the frontend's login-redirect guard (`web/src/router/index.ts`) and `App.vue`'s logged-in-only shell were removed — all API routes and pages are open, temporarily, until login is re-enabled. The auth controller/service/store/views are untouched, so re-enabling is just re-adding the middleware calls and the router guard.

**User management** (`internal/controllers/user_controller.go`, `internal/services/user_service.go`): plain CRUD over `models.User` behind `/api/users`, mirroring the Task/TaskGroup controller→service shape. `User.Status` was changed from a `bool` to the same `enabled`/`disabled` string convention as `Task.Status`/`TaskGroup.Status` (`models.STATUS_ENABLED`/`STATUS_DISABLED`), so all three share one vocabulary. `AuthService.Authenticate` checks `Status` after the bcrypt password compare and returns `services.ErrUserDisabled` for a `disabled` account, which `AuthController.LoginHandler` maps to a 401 with a distinct message — this check runs on every login attempt regardless of whether `JWTAuthMiddleware` is mounted, since it's inside `Authenticate` itself, not the middleware.

**Response envelope**: all API responses go through `pkg/response.Success`/`Fail`, which wrap payloads in a `{code, message, data, error, trace}` shape and pull `trace_id` from gin context (set by `OpenTracingMiddleware`). Controller error paths intentionally do **not** put the raw Go `error` into the `error` field for unexpected (500-class) failures — it's logged server-side (via `logger.WithTrace(c)`, so it's tied to the same `trace_id` returned to the client) instead, so a bug report can reference the trace without leaking internal error strings to callers. Structured validation errors (`utils.FormatValidationErrors`, per-field `{field, tag, param}`) are the exception and are still returned to the client, since the frontend parses them.

**Logging** (`pkg/logger/logger.go`): `logger.Log` writes to two sinks with different formats — stdout gets the colored, human-readable `LogFormatter` (now includes `entry.Data`, so `trace_id` and `WithError(err)` actually show up; earlier versions silently dropped all fields); the log file (`logs/app.log`, rotated via `lumberjack`) gets JSON through a `logrus.Hook` (`fileHook`), so `jq 'select(.trace_id=="...")' logs/app.log` works. Level is controlled by `config.AppConfig.LogLevel` (populated from the `.env`/env `LOG_LEVEL` key — not read directly via `os.Getenv`, so it goes through the same `SetDefault`/required-key handling as everything else in `config.LoadConfig`), falling back to `debug` in development (`Config.IsDevelopment()`), `info` otherwise. `OpenTracingMiddleware` (`internal/middleware/tracing_middleware.go`) reuses an incoming `X-Request-ID` header as `trace_id` when present (otherwise generates one) and echoes it back as a response header, so it round-trips through callers that set it.

**Frontend serving (no CORS)**: the Vue frontend (`/web`) is served same-origin in production via `r.Static`/`r.NoRoute` in `router.go` (serving `web/dist`, with an SPA fallback to `web/dist/index.html` for non-`/api` paths). There is no CORS middleware — it was removed because it was never actually needed: in development, `web/vite.config.ts` already proxies `/api` to the Go backend with `changeOrigin: true`, so the browser's requests stay same-origin against the Vite dev server itself, and production is same-origin by construction. If a future consumer needs true cross-origin browser access (a separate frontend, an embedded widget), CORS middleware would need to be reintroduced deliberately for that case.

**Frontend run-now polling** (`web/src/components/RunTaskDialog.vue`): shared by `TaskListView.vue` and `TaskDetailView.vue`. Before calling `POST /tasks/:id/run` it fetches the task's most recent `TaskExecutionLog` id as a baseline, then polls `GET /tasks/logs/` every second and treats any log whose `id` sorts lexically greater than the baseline as belonging to this batch — relying on `xid` ids being chronologically sortable as plain strings (timestamp-prefixed), rather than on `started_at` (only second-precision, and receiving no batch/run identifier from the backend to filter on directly). Closing the dialog only stops the client-side polling; it does **not** call `DELETE /tasks/:id/run`, so an in-progress batch keeps running server-side unless the user explicitly clicks cancel.

**Go version**: `go.mod` pins `go 1.24.4`. When bumping `google.golang.org/grpc` or `github.com/jhump/protoreflect`, check each candidate version's own `go.mod` `go` directive first — `go get`/`go mod tidy` will otherwise silently bump this project's `go` directive to satisfy a newer dependency.
